把之前在网上看到的一份 AI 编码规则记在这里，作为我的 `AGENTS.md` 基础版本，方便以后复制到项目里，再补充项目自己的约定。

这份规则关注四件事：实现前说明假设与取舍，只写解决问题所需的代码，把改动限制在需求范围内，以及用明确的成功标准验证结果。

## 英文出处

这份规则来自 [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) 项目中的 [CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md)。项目由 `forrestchang` 整理，原仓库地址是 [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)，目前已迁移到 `multica-ai` 组织下。

项目的名称是 **Karpathy-Inspired Claude Code Guidelines**。[README](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/README.md) 说明，这些原则根据 Andrej Karpathy 对 LLM 编码常见问题的观察整理而来。原文件使用 `CLAUDE.md` 作为文件名，这里记录的是我使用的 `AGENTS.md` 中文版。

四个章节、具体细则和结尾的效果判断都能在英文原文中对应找到。为方便以后核对，也保留一份 [英文源文件的固定版本链接](https://github.com/multica-ai/andrej-karpathy-skills/blob/8462496b34419f20b32778610571ac723e91f94c/CLAUDE.md)。

## AGENTS.md 全文

下面是完整的 Markdown 内容，可以直接复制。保留原有中文规则的表述，仅统一标题层级、加粗和代码块格式。

````markdown
# AGENTS.md

## 1. 编码前先思考

**不要假设，不要掩盖疑惑，明确说明取舍。**

实现前：

- 明确说明你的假设。不确定时先询问。
- 存在多种解释时，把它们列出来，不要悄悄选择其中一种。
- 如果有更简单的方案，主动指出；必要时提出反对意见。
- 如果存在不清楚的地方，先停止。明确指出困惑点并询问。

## 2. 简单优先

**只编写解决问题所需的最少代码，不做推测性实现。**

- 不实现用户没有要求的功能。
- 不为一次性代码增加抽象。
- 不增加用户没有要求的“灵活性”或“可配置性”。
- 不为不可能出现的场景增加错误处理。
- 如果写了 200 行但 50 行就能解决，应重新实现。

问自己：“资深工程师会不会认为这套实现过于复杂？”如果会，就继续简化。

## 3. 精准修改

**只修改必须修改的内容，只清理自己产生的问题。**

编辑现有代码时：

- 不要顺手“改进”相邻代码、注释或格式。
- 不要重构没有问题的代码。
- 遵循项目现有风格，即使你个人会采用其他写法。
- 如果发现无关的死代码，可以指出，但不要删除。

如果本次修改产生了遗留内容：

- 删除因本次修改而不再使用的 import、变量或函数。
- 除非用户明确要求，不要删除修改前就存在的死代码。

判断标准：每一行变更都应能直接追溯到用户需求。

## 4. 目标驱动执行

**先定义成功标准，再循环执行直到验证通过。**

把任务转换为可验证目标：

- “增加校验” → “先为非法输入编写测试，再使测试通过”
- “修复问题” → “先编写能够复现问题的测试，再使测试通过”
- “重构 X” → “确认重构前后测试都通过”

对于多步骤任务，先给出简短计划：

```text
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

明确的成功标准可以让你独立循环推进。模糊的标准（例如“让它能用”）会导致不断澄清。

**这些规则生效的表现：**diff 中不必要的改动更少，因过度设计导致的返工更少，澄清问题发生在实现前而不是出错后。
````

## 使用时的取舍

英文原文开头还说明了两个前提：这些规则可以与项目自己的指令合并使用；它们更偏向谨慎，对于简单任务应根据实际情况判断。

我把这两点也记下来。具体项目的技术栈、构建命令、验证方式和目录约定，可以在这份基础规则后继续补充。是否起作用，就用规则最后写的三个现象来观察：无关改动是否减少、过度设计造成的返工是否减少、需要澄清的问题是否更早被提出来。
